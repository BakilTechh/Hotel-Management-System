🎯 4. Empat Pilar OOP (Analisis Implementasi Aktual)

🔒 1. ENCAPSULATION

Pengertian: Membungkus data dan perilaku dalam class, mengontrol akses agar data tidak diubah sembarangan.

Bukti Implementasi:
  • PromoVoucher._consume_quota() - Protected method, kuota hanya dikurangi via method terkontrol
  • ServiceOrder.transition_to() - Satu-satunya pintu ubah status, divalidasi oleh _can_transition()
  • Payment.__is_verifiable() - Private method (name mangling)
  • Booking.hitung_total_biaya() - Mengenkapsulasi kalkulasi kompleks
  • @property - display_name, initials, completeness, durasi_malam

🧬 2. INHERITANCE

Pengertian: Class turunan mewarisi atribut/method dari class induk (relasi "is-a").

Bukti Implementasi:
  • TimeStampedModel (core/models.py) - Abstract Base Class
  • BaseTransaction(TimeStampedModel) - Booking, PromoVoucher, Payment, Review, PaymentEvent mewarisi
  • BasePaymentProcessor(ABC) - Abstract Base Class untuk payment processors
  • ManualTransferProcessor(BasePaymentProcessor) - Single inheritance
  • GatewayPaymentProcessor(BasePaymentProcessor) - Single inheritance

🎭 3. POLYMORPHISM

Pengertian: Satu interface, banyak implementasi. Objek berbeda bisa dipanggil dengan cara yang sama.

Bukti Implementasi:
  • Method Overriding: RoomServiceMenuItem.clean(), semua __str__()
  • Via Inheritance: BasePaymentProcessor.charge()/refund() diimplementasikan berbeda
  • Duck Typing: EmailNotifier, SMSNotifier, InAppNotifier - punya send() tanpa inheritance kuat
  • State-based: ServiceOrder behavior beda per fulfillment, Booking.payment_status_group()

🎨 4. ABSTRACTION

Pengertian: Menyembunyikan detail kompleks, hanya menampilkan interface yang diperlukan.

Bukti Implementasi:
  • reservations/services.py - Service layer menyembunyikan locking, transaksi, validasi kompleks
  • Booking.available_rooms() - Abstraksi query kompleks (bentrok, blocking status)
  • BasePaymentProcessor(ABC) - Interface tanpa implementasi detail
  • TimeStampedModel - Abstraksi kebutuhan timestamp bersama

Contoh Kode - Enkapsulasi ServiceOrder

# chatbot/models.py - ENCAPSULATION
class ServiceOrder(models.Model):
    def _can_transition(self, new_status):
        """Protected method: validasi transisi"""
        allowed = self.ALLOWED_TRANSITIONS.get(self.status, ())
        if new_status not in allowed: return False
        if new_status == self.STATUS_READY and not self.is_pickup: return False
        if new_status == self.STATUS_DELIVERED and self.is_pickup: return False
        return True

    def transition_to(self, new_status, actor=None, note=''):
        """SATU-SATUNYA pintu untuk ubah status pesanan"""
        if not self._can_transition(new_status):
            return False
        old_status = self.status
        self.status = new_status
        self.save(update_fields=['status', 'updated_at'])
        ServiceOrderStatusLog.objects.create(
            order=self, status=new_status, note=note or '', changed_by=actor,
        )
        return True

Contoh Kode - Inheritance + Polymorphism (Payment Processor)

# reservations/payment_processors/base.py - ABSTRACTION + INHERITANCE
from abc import ABC, abstractmethod

class BasePaymentProcessor(ABC):
    @abstractmethod
    def charge(self, booking, amount):
        pass
    
    @abstractmethod
    def refund(self, payment, amount):
        pass

# manual_transfer.py - POLYMORPHISM (inheritance)
class ManualTransferProcessor(BasePaymentProcessor):
    def charge(self, booking, amount):
        return {"method": "MANUAL_TRANSFER", "status": "PENDING_VERIFICATION"}
    
    def refund(self, payment, amount):
        from ..services import request_refund
        request_refund(payment, reason="Refund via manual transfer")
        return {"method": "MANUAL_TRANSFER", "status": "REFUND_PENDING"}

# gateway.py - POLYMORPHISM (different implementation)
class GatewayPaymentProcessor(BasePaymentProcessor):
    def charge(self, booking, amount):
        return {"method": "GATEWAY", "status": "AWAITING_PAYMENT"}
    
    def refund(self, payment, amount):
        return {"method": "GATEWAY", "status": "REFUND_INITIATED"}

📈 8. Evaluasi Desain OOP

💪 Kekuatan

  • Service Layer: reservations/services.py memisahkan logika bisnis dengan baik
  • Base Classes: Penggunaan TimeStampedModel & BaseTransaction mengurangi duplikasi
  • Controlled Transitions: ServiceOrder.transition_to() dengan validasi ketat
  • Voucher Protection: Penggunaan method protected untuk kuota voucher
  • Payment Safety: Perubahan status terpusat di service layer
  • Polymorphism Demo: Penambahan payment processors & notifiers sangat baik untuk demonstrasi

⚠️ Kekurangan

  • Booking Model: Beberapa field masih bisa di-assign langsung (total_biaya_akhir masih public)
  • Inheritance Depth: Hierarki masih relatif dangkal
  • Interface Usage: Payment processors baru ditambahkan tapi belum diintegrasikan ke flow utama
  • Private Methods: Masih sedikit penggunaan __private, lebih dominan _protected

💡 Rekomendasi

  • Integrasi Processors: Gunakan BasePaymentProcessor di flow pembayaran
  • Read-only Properties: Jadikan total_harga_dasar/diskon/pajak/total_biaya_akhir read-only
  • More ABC: Pertimbangkan BaseServiceOrder untuk hierarki layanan
  • Type Checking: Tambahkan validasi dengan isinstance() untuk demonstrasi polymorphism
  • Consistent Naming: Pertahankan konvensi _protected & __private yang sudah dimulai

Kesimpulan

Proyek Hotel Management System ini telah menerapkan ke-4 pilar OOP dengan cukup baik, terutama di modul reservations dan chatbot. Penambahan core/models.py, payment_processors/, dan core/notifiers/ memperkuat demonstrasi inheritance, polymorphism, abstraction, dan encapsulation sesuai materi perkuliahan. Implementasi bersifat nyata berdasarkan kode sumber, bukan rekaan.
